# 개발비서와 지식 인계 중심의 작업 수명 설계안

작성일: 2026-09-25<br>
상태: 1단계와 2단계 보존 핵심 코드 반영 · 자동 인계·보존 source 갱신·기준 복구·문서 정리는 미구현 제안<br>
검토 기준: Plan2Agent `600417e` / BuildLore `23db411`

## 1. 목표와 범위

P2A는 개발을 진행하면서 사용자가 현재 상황을 이해하도록 설명하고, 원래 목적에서 벗어날 조짐에 대해 근거 있는 의견을 준다. 개발 중 문서는 현재 작업에 필요한 기억으로 사용한다. 완료 후에는 다음 개발에 필요한 내용을 지식저장소로 인계하고, 인계가 확인된 작업 문서를 정리할 수 있게 한다.

사용자가 제시한 방향을 다음 두 결과로 구체화한다.

1. **개발 중:** 무엇이 되었고, 무엇을 하고 있으며, 현재 방향에 어떤 의견이 있는지 짧게 알린다. 의견만으로 개발을 중단하거나 새로운 승인을 요구하지 않는다.
2. **개발 후:** 현재 제품 지식, 결정 이유, 실패에서 얻은 교훈, 검증 범위와 남은 일을 지식저장소에 남긴다. 종료된 반복 개발과 유지보수의 작업 문서는 다음 작업의 필수 입력에서 제외한다.

1단계의 개발비서 행동과 제한된 BuildLore 읽기 연결은 실행 지침·adapter에 반영했다. 2단계 중 명시적 `p2a knowledge capture`와 BuildLore `handoff import/list/read/verify` 보존 경로를 추가했다. 사용법과 제약은 [CLI 참고서](cli-reference.md#완료-자료-고정--p2a-knowledge-capture)에 통합했다. 아래의 전체 수명 설계 중 자동 완료 인계, 보존 source 기반 위키 갱신, 기준 복구, 참조 전환과 정리는 여전히 제안이다. 승인 상태와 보관 정책은 바꾸지 않았고 실제 작업 문서 삭제도 수행하지 않는다. 후속 구현까지 정식 문서로 통합한 뒤에는 이 제안서를 별도 장기 문서로 계속 관리할 필요가 없다.

## 3. 개발 중 비서의 행동

### 3.1 판단에 사용하는 자료

다음 정보를 구분해 설명한다.

- **현재 의도:** 사용자의 최신 요청과 선택, 현재 작업의 목표. 사용자가 방향을 수정하면 그 변경을 반영한다.
- **현재 사실:** 실제로 읽은 코드와 diff, 실행한 검사 결과, 아직 확인하지 못한 부분.
- **이전 기억:** BuildLore에 기록된 결정 이유, 제약, 실패한 접근, 당시의 검증 범위.
- **의견:** 위 자료를 비교해 예상한 영향과 권장하는 다음 행동. 추론을 확인된 사실처럼 표현하지 않는다.

사용자의 명시적인 방향 변경은 현재 작업 기준에 반영한다. 과거 Wiki 내용 자체를 새 권한이나 승인으로 해석하지 않는다. 기존 실행 계약을 갱신해야 하는 실제 요청 변경은 기존 경로로 반영하되, 비서가 낸 우려만으로 변경 요청이나 차단 상태를 만들지 않는다.

### 3.2 언제 무엇을 알리는가

| 계기 | 설명 |
| --- | --- |
| 작업 시작·재개 시 맥락 설명이 필요함 | 이번 목표, 현재까지 된 부분, 바로 진행할 일 |
| 사용자 기능의 일부가 동작하거나 검증됨 | 가능해진 것, 확인한 범위, 남은 것 |
| 중요한 설계 선택 또는 새 사실이 생김 | 선택 이유, 예상 영향, 필요한 경우 대안 |
| 같은 실패가 반복되거나 변경이 커짐 | 기존 가설의 한계, 목표와의 관계, 권장 접근 |
| 사용자가 상태나 방향을 질문함 | 질문에 직접 답하고 요청된 개발을 계속함 |
| 개발 완료 | 실제 결과, 검증 범위, 미해결 사항, 지식 인계·정리 상태 |

일반 브리핑은 2~4문장으로 작성하고 방향 의견은 중요한 쟁점 하나에 집중한다. 파일 편집이나 도구 호출마다 보고서를 만들지 않는다. 실행 도구가 요구하는 진행 알림 주기는 따르되, 변화가 없을 때 새로운 검토 절차를 만들지 않는다.

### 3.3 방향 검토 기준

검토 질문은 “현재 변경이 이번 사용자 문제를 해결하는 데 도움이 되는가”다. 예를 들어 요구에 비해 구조·설정·의존성이 커지는지, 원인 확인 없이 같은 수정이 반복되는지, 테스트한 조건과 실제 사용자 조건이 다른지 살핀다. 파일 수 증가, 계획 수정, 과거 결정과의 차이만으로 이탈을 단정하지 않는다.

의견에는 **관찰 → 목표에 미치는 영향 → 권고 → 이어갈 행동**을 담는다. 근거가 부족하면 불확실성을 밝힌다. 사용자의 응답이 없어도 이미 요청한 개발은 계속한다. 사용자가 의견을 보류하거나 다른 방향을 선택하면 이를 기억하고, 새 근거나 영향 변화가 생기기 전에는 같은 지적을 반복하지 않는다.

BuildLore 대용량 위키 작업을 가정한 안내 예시:

> 큰 문서 묶음에서도 위키 생성이 끝까지 되는 것이 이번 목표입니다. 현재는 불필요한 인용 정보 생성을 줄이고 있습니다. 저장 형식 전체를 바꾸면 변경이 커질 수 있어, 우선 기존 형식을 유지한 상태에서 대용량 입력을 검증하는 편을 권합니다. 다음에는 생성부터 읽기까지 이어지는 동작을 확인하겠습니다.

진행 설명과 의견은 대화에서 제공한다. 재개에 필요한 최신 의도·보류한 의견·다음 행동만 기존 작업 notes에 갱신한다. 유사한 `progress.md`, `review.md`, `summary.md`를 매번 생성하지 않는다.

### 3.4 BuildLore 조회 정책

설정된 프로젝트에서는 첫 시도에도 현재 작업과 관련된 기억을 읽을 수 있도록 실행 지침을 변경한다. 시작·재개 또는 의미 있는 방향 변화에서 `memory(task, progressive=true)`를 사용하고, 의견의 근거가 필요할 때만 해당 항목을 `lookup`한다. 초기 조회 한 번과 필요한 근거 묶음 조회를 기본으로 하며, 이미 확인한 범위는 재사용한다.

동일 프로젝트·generation·source digest를 확인한다. 조회 도중 generation이 바뀌면 이전 결과와 섞지 않는다. `sourceRevision`은 근거 원본의 식별·무결성, `codeRevision`은 기록된 검증 대상 코드, `repositoryRevision`은 관찰한 저장소 HEAD로 구분한다. 원본 revision이나 관찰한 HEAD를 코드 검증 증거로 대신하지 않는다. 검증 대상이 없거나 현재 코드와 다르면 미확인 또는 과거 기록임을 표시한다. 근거 ID가 있다는 것과 본문을 읽어 주장을 확인했다는 것도 구분한다.

현재 `memory`·`lookup`은 승인된 generation의 조회 경로다. 위키 반영 전의 보존 인계는 별도의 **보존 객체 직접 조회 경로**인 `handoff list/read/verify`로 필요한 경우에만 읽는다. 현재 목록은 프로젝트·작업 ID로 제한하고 선택한 객체의 본문·구조화 기준·digest를 조회한다. 현재 상태는 모두 위키 반영 대기이며, 보존됐다는 이유로 승인된 현재 사실처럼 memory 결과에 섞지 않는다. 기준 계보·영향 범위 기반 탐색과 위키 기각·채택 상태 연결은 후속 구현 대상이다.

조회는 시간·출력 예산을 가진 보조 작업이다. 미설정·빈 결과·실패·예산 초과이면 현재 코드와 사용자 요청으로 계속한다. 지식이 없다는 이유로 프로젝트 전체를 다시 설명해 달라고 요구하지 않는다. 조회에 sync, 위키 재작성, 승인, commit, push를 숨은 후속 작업으로 붙이지 않는다.

## 4. 자료의 수명과 저장 위치

| 자료 | 개발 중 | 종료 후 |
| --- | --- | --- |
| 코드·테스트·README·API/운영 안내 | 제품 저장소에서 수정 | 제품의 일부로 유지 |
| 범위·구현 계획·task·실행 기록·작업용 근거 | 현재 작업 공간에서 사용 | 인계 및 참조 전환 확인 후 정리 가능 |
| 중간 보고·일회성 실험·임시 설치 환경 | 필요한 동안만 유지 | 필요한 근거만 인계하고 정리 |
| 제품의 현재 동작·설계 이유·교훈·한계·남은 일 | 관련 부분 조회 | 지식저장소에서 주제별로 갱신 |
| 다음 작업의 기준과 그 출처 | 현재 실행 계약 사용 | 지식저장소의 구조화된 완료 기준으로 보존 |
| 프로젝트 설정·연결·현재 기준 포인터 | 로컬에서 사용 | 최소 상태만 유지 |

사용자 제공 문서와 제품 문서는 작업 문서라는 이유로 정리하지 않는다. 대상은 P2A와 실행 agent가 소유한 종료 작업의 산출물이다. `.plan2agent` 밖에 작성한 임시 설계안·조사·체크리스트도 작업 소유와 용도가 확인되면 포함한다. 기존 문서의 소유가 불명확하면 정리 후보로만 표시한다. 1차 구현에서는 프로젝트 공용 `decisions.jsonl`을 호환성 예외로 유지한다. 이 원장은 `seq`와 이전 해시로 연결되므로 일부 행을 삭제하는 방식으로 줄이지 않는다.

위키에 채택한 지식은 현재 주제에 통합하고 변경 이력은 지식저장소 Git으로 추적한다. 원본 정리를 위한 근거 보존과 위키의 현재 사실로 채택하는 일은 분리한다. 완료 보고서 전체를 매번 새 위키 페이지로 복사하지 않는다. 다음 판단에 필요한 근거는 정확한 발췌·구조화 기록·재현 가능한 코드 위치로 보존하며, 원본이 Git에 없거나 재현 불가능하면 필요한 원문도 정제 후 저장한다.

## 5. 완료 후 지식 인계

### 5.1 사용자에게 보이는 흐름

```text
현재 코드 + 관련 프로젝트 기억 + 사용자 요청
  → 개발·진행 설명·방향 의견
  → 개발과 검증 완료
  → 필요한 근거와 다음 작업 기준을 독립적으로 보존
  → 보존 본문·기준의 직접 조회와 참조 전환 확인
  → 종료 작업 문서 정리

보존된 내용 → 기존 위키 작성·검토·활성화 정책에 따라 별도로 반영
```

개발 완료, 근거 보존, 위키 반영, 문서 정리 상태는 구분한다. 예: “개발과 검증은 완료됐습니다. 근거와 다음 작업 기준은 보존해 작업 문서를 정리했고, 위키 반영은 대기 중입니다.” 보존 자체가 실패했다면 원본을 남기되, 완료 task를 다시 열거나 다음 개발을 일괄 차단하지 않는다. 다음 개발·위키 갱신까지 이어지는 전체 검증은 매 완료 건의 작업이 아니라 구현·릴리스 호환성 검사다.

### 5.2 장기 보존할 내용

다음 항목 중 해당 작업에서 달라진 내용만 반영한다.

1. **결과:** 실제 구현된 동작과 아직 구현되지 않은 부분.
2. **결정:** 선택 이유, 의미 있는 대안, 유지하거나 변경한 조건.
3. **교훈:** 실패 조건, 확인한 원인, 해결 방법, 회귀 방지 방법.
4. **검증:** 검사 대상 코드 revision, 실행 명령, 결과, 검증 범위와 한계.
5. **남은 일:** 미해결 문제, 알려진 제약, 사용자가 보류한 항목.
6. **다음 작업 기준:** 목표·유지할 동작·유효한 제약·검증 기준과 이를 뒷받침하는 결정의 출처.

구현됐다는 진술, 검사를 정의했다는 사실, 실제 실행으로 통과했다는 사실을 구분한다. 의견은 의견으로 보존하며 반복 조회만으로 확정된 제품 사실로 바꾸지 않는다.

### 5.3 최소 인계 데이터 제안

기존 BuildLore project-scoped source/generation과 P2A current development contract를 재사용한다. 다음 두 역할만 추가하며, 별도 완료 보고서 묶음이나 다단계 승인 원장은 만들지 않는다.

| 역할 | 필요한 정보 | 보관 |
| --- | --- | --- |
| 인계 본문 | 프로젝트·제품 저장소·작업 식별, 원본/검증 코드/관찰 HEAD의 구분, 검증 대상 제품 내용 digest, 선행 기준 ID·해시, 영향 범위와 명시적 대체 관계, 구조화된 완료 기준, 선택한 지식과 정제된 근거, 기존 승인·결정의 대상·계약 digest·출처 | 지식저장소의 보존 source. 내용 해시로 식별 |
| 인계 확인 기록 | 인계 본문 식별·해시, 지식저장소 식별·보존 commit, 독립 조회·참조 전환 결과, 기준 반영 결과, 위키 반영 상태와 채택된 경우의 generation | 로컬의 작은 포인터/재시도 상태. 보존된 본문·목록에서 재구성하고 로컬 참조 전환 여부는 다시 확인 |

인계 본문이 담긴 commit ID를 같은 본문 안에 넣어 순환 해시를 만들지 않는다. commit 참조는 저장 후 로컬 확인 기록에 결합한다. 새 환경에서는 인계 식별자로 보존된 본문을 찾아 같은 내용을 검증한다.

완료 시점에 인계에 필요한 내용을 고정한다. 후속 작업이 공용 spec이나 실행 기록을 바꾼 뒤 재시도하더라도 이전 완료 내용을 새로 읽어 덮어쓰지 않는다. 연결 실패 시 이 고정본과 필요한 원본을 로컬에 유지하고 보존 성공 뒤 정리한다. 동일 프로젝트·작업·내용 해시의 인계는 재실행해도 중복 지식이나 중복 완료 기록을 만들지 않는다.

Git HEAD만으로 미커밋 작업을 식별하지 않는다. 검증된 제품 revision과 필요한 patch/본문 근거를 포함한다. 제품 내용 digest의 대상은 코드·설정 등 명시된 검증 입력이며, 정리할 작업 문서는 제외한다. 검증 당시와 조회 시 같은 계산 규칙을 사용한다. 필수 근거·다음 작업 기준·살아 있는 참조를 보존하지 못하면 해당 자료의 정리를 보류한다. 재사용 가치나 참조가 없는 일회성 중간물은 인계하지 않고 폐기 대상으로 구분할 수 있다.

완료 기준은 구조화된 계약 값에서 만들며 위키 산문을 다시 읽어 승인 의미를 추정하지 않는다. 출처 정보는 유지하되 다음 작업에서 삭제된 원본 파일을 열어야만 해석되는 참조는 제거한다. 이 기준은 이전 상태의 근거이며, 이후 새 작업의 권한을 자동으로 부여하지 않는다.

### 5.4 임시 source에서 보존 source로 전환

BuildLore의 현재 source 관리에는 이 전환 기능이 없다. 다음 동작을 추가해야 한다.

1. P2A 산출물을 기존 sanitizer 경계 안에서 읽고 필요한 내용과 근거를 보존 source 후보로 작성한다.
2. 지식저장소가 보존 source 목록을 소유한다. 목록에 원래 프로젝트·작업·source ID·당시 revision·원문 위치/범위·정제된 내용 digest를 연결한다. 후보는 기존 승인 지식을 바꾸지 않는다.
3. 새 source resolver는 live source와 보존 source를 구분한다. 보존 source는 저장된 본문을 읽으며 삭제된 checkout 경로를 다시 열지 않는다. snapshot 생성과 activation 재검증이 동일한 resolver와 계승 관계를 사용한다.
4. 보존 source 목록·근거·구조화된 기준을 복구 가능한 지식저장소 commit에 저장한다. 원본 경로에 접근하지 않는 직접 조회로 본문 digest, 필요한 참조의 보존, 기준의 파싱·복구를 확인한다. 이 확인에 새 위키 generation이나 승인을 요구하지 않는다.
5. 확인 기록을 받은 뒤 제품 checkout의 source 선언과 P2A 참조를 해당 보존 source로 전환한다. 기존 선언의 예상 digest가 맞는지 검사하고 종료 작업의 정확한 참조만 전환한다. 원본은 이 전환이 끝날 때까지 유지한다. 전환 완료 후에는 위키 반영 대기 여부와 별개로 정리할 수 있다.
6. 위키 반영은 별도로 기존 작성·검토·활성화 정책을 따른다. 기각되거나 대기 중인 후보를 승인된 현재 사실로 표시하지 않으며, 그 상태도 보존한다. 사실 채택과 무관하게 필요한 과거 근거의 조회는 유지한다.

현재 제품 checkout의 `.buildlore/sources.json`과 지식저장소는 서로 다른 Git 저장소일 수 있다. 두 저장소에 원자적 commit이 있다고 가정하지 않는다. 지식저장소의 보존이 먼저 완료되고 로컬 전환이 실패하면 원본을 유지한 채 전환만 재시도한다. 불완전한 보존 목록을 조회 가능한 완료 상태로 노출하지 않는다. 같은 경로가 다음 작업에서 재사용될 수 있으므로 `current-spec.json`, `run-index.json`이나 source root 전체를 영구 제외하지 않는다.

원본 문서의 정리는 제품 사실의 삭제와 다르다. 다음 갱신에서도 해당 근거가 남아 있어야 하며, 정리만으로 `SOURCE_MISSING`이나 무조건적인 stale 판정이 생기면 안 된다. 실제 코드가 변경돼 과거 근거가 오래된 경우는 계속 구분한다.

### 5.5 실패와 권한 처리

프로젝트에서 지식 인계·정리 정책을 선택할 때 대상 저장소, 허용한 로컬 쓰기·commit, 정리 범위를 정한다. 이후 같은 범위의 정상 작업마다 재승인을 요구하지 않는다. 이 정책 선택이 기존 위키 승인·활성화 권한을 자동으로 위임하는 것은 아니다. 위키에 별도 선택이 필요하면 위키 반영만 대기시키며, 독립 보존과 참조 전환이 확인된 문서는 정리할 수 있다. 조회 권한만 있는 연결에는 인계 쓰기를 시도하지 않는다.

| 상황 | 개발 결과 | 인계·정리 |
| --- | --- | --- |
| 지식저장소 없음 또는 연결 실패 | 완료 유지 | 기존 자료 유지, 현재 코드와 로컬 기준으로 다음 작업 가능 |
| sanitizer, 보존 본문 작성 또는 commit 실패 | 완료 유지 | 실패한 단계부터 재시도, 고정본과 필요한 원본 유지 |
| 지식 보존 성공, 원본 없는 읽기 검증 실패 | 완료 유지 | 정리 보류, 끊어진 근거를 수정 |
| 보존·조회·참조 전환 성공, 위키 작성·승인·활성화 대기 또는 실패 | 완료 유지 | 위키 반영만 재시도·대기, 문서 정리 가능 |
| 현재 기준이 먼저 갱신되어 늦은 인계와 충돌 | 완료 유지 | 인계는 이력으로 보존, 현재 기준은 유지. 참조 전환이 확인된 문서는 정리 가능 |
| 인계 도중 사용자 자료나 작업 상태 변경 | 완료 유지 | 정리 계획 재계산, 변경된 파일 보존 |
| 일부 정리 실패 또는 중단 | 완료 유지 | 인계 기록을 유지하고 남은 대상만 재처리 |

지식저장소의 사용자 변경을 한꺼번에 commit하지 않는다. 원격 push, 배포, 유료 서비스 호출은 이 로컬 인계 정책에 자동 포함하지 않는다.

### 5.6 늦은 인계와 동시 작업

보존 성공은 현재 기준 교체와 다르다. 기존 generation 불일치·대체 사실 복귀 방지와 P2A baseline 고정을 재사용하되, 지식 generation과 별개인 완료 기준의 선후관계를 추가한다. 인계 본문에는 작업이 출발한 선행 기준의 ID·해시와 제품 revision 계보, 변경한 사실·제약의 범위, 대체하려는 항목을 기록한다. 기준을 갱신할 때는 기존 잠금 안에서 예상 선행 포인터가 현재 값과 같은지 확인하는 조건부 갱신을 사용한다. 동일 프로젝트라도 다른 코드 계보의 기준을 하나의 전역 최신 값으로 덮어쓰지 않는다.

A 완료 후 인계가 지연되고 B가 먼저 반영됐다면, A 재시도는 먼저 이력으로 보존한다. 시간순 도착이나 내용 해시의 중복 방지만으로 B의 기준·사실을 A로 되돌리지 않는다. 영향 범위가 겹치지 않으면 현재 기준을 선행으로 하는 새 통합 기준을 검증해 만들 수 있다. 겹치거나 계보를 확인할 수 없으면 현재 기준을 유지하고 조정할 차이만 알린다. 이 처리는 다음 개발의 추가 승인 gate가 아니다.

위키 갱신에도 같은 대체 관계를 전달한다. 보존 목록에 늦게 들어온 과거 기록을 최신 제품 사실로 채택하지 않으며, 후보를 만든 뒤 활성 generation이 바뀌었다면 현재 generation에 대한 차이를 다시 검토한다.

## 6. 작업 문서를 지운 뒤의 P2A 동작

### 6.1 다음 반복의 시작과 취소

현재 `createOpenBaselineSnapshot`은 current development contract로 baseline intake/spec를 만든다. 이 입력을 **활성 작업의 계약** 또는 **검증된 완료 기준**에서 받을 수 있도록 분리한다.

완료된 작업의 디렉터리가 없을 때 `next`, `info`, 새 iteration 열기는 지식저장소의 완료 기준과 최소 로컬 포인터로 처리한다. 다음 작업에 필요한 문서는 그 작업을 시작할 때만 만든다. 직전 작업의 모든 Gate·graph·run을 복원하는 방식으로 시작하지 않는다.

기준은 지식저장소의 가장 최신 generation이 아니라 **현재 제품 checkout에 적용 가능한 완료 기준**으로 선택한다. 프로젝트·제품 저장소 식별, 검증 대상 `codeRevision`과 제품 내용 digest, 명시된 선행·대체 관계를 확인한다. 브랜치 이름이나 기록 시각만으로 적용 가능하다고 보지 않는다. 미커밋 변경이 있으면 HEAD 일치만으로 충분하지 않으며, 검증 대상이나 digest가 없으면 현재 검증 기준이라고 주장하지 않는다.

선택한 기준의 ID·해시는 작업 시작 시 고정한다. 승인된 기억을 함께 읽었다면 해당 generation도 기록하되, 보존 기준의 선택에 승인 generation을 필수로 요구하지 않는다. 새 지식이 도착해도 활성 작업의 기준을 몰래 교체하지 않는다. main의 R2 기록만 있고 현재 checkout이 release의 R1이면 R1에 맞는 보존 기준을 찾고, 없으면 R2는 참고 이력으로만 읽는다. 대응 기준이 없어도 현재 코드·최신 사용자 요청·사용 가능한 로컬 계약으로 진행하며, 없는 승인을 만들어내거나 과거 문서 복원을 필수 gate로 삼지 않는다.

새 작업을 취소할 때도 이미 삭제한 이전 graph를 요구하지 않고 같은 완료 기준으로 돌아간다. 진행 중 작업의 resume, 실행 권한, 검증 근거 검사는 현재 파일과 기존 계약을 계속 사용한다. 파일이 없다는 이유만으로 완료·인계 상태를 추정하지 않는다.

실행 재개용 최소 기준과 제품 전체의 기억은 구분한다. 기존 baseline 생성기는 일부 사용자·데이터 모델·외부 연동 필드를 채우지 않으므로 그 결과만으로 원래 제품 의도가 모두 보존됐다고 판단하지 않는다. 관련 제품 의도와 결정 이유는 지식 인계 내용에 별도로 남긴다.

### 6.2 유지보수

상시 maintenance 컨테이너 전체를 종료 대상으로 취급하지 않는다. 완료된 task/run 묶음만 인계·정리하며, 대기·실행 중·실패·재개 예정 작업은 유지한다. task가 참조되는 동안 필요한 작은 완료·의존성 기록은 남긴다.

maintenance 진입점은 프로젝트 식별과 해당 작업 상태를 읽도록 분리해 과거 feature iteration 폴더에 의존하지 않게 한다. 유지보수의 작은 목표로 프로젝트 전체 완료 기준을 덮어쓰지 않고, 영향을 준 사실·제약·검증 revision만 반영한다.

### 6.3 최소 로컬 상태와 호환성

프로젝트 설정, 설치 manifest, 유효한 프로젝트 원칙, 현재 기준 포인터와 필요하면 그 기준 한 개의 검증된 캐시를 유지한다. 캐시는 현재 내용만 가지며 과거 작업 문서를 누적하지 않는다. 지식저장소를 사용할 수 없어도 이미 확보한 기준으로 작업을 시작할 수 있다. 기존 프로젝트의 공용 결정 원장은 1차 호환성 예외로 그대로 유지한다. 기존 원장의 일부를 잘라 새 시작점으로 만들거나 과거 승인 행을 다시 쓰지 않는다.

**새 checkout 복구는 별도 초기화 경로로 추가한다.** 기존 로컬 원장이 없는 환경에서는 보존 기준을 검증한 뒤, 그 출처에 연결된 새 로컬 원장을 시작한다. 최소 복구 메타데이터는 프로젝트·제품 저장소 식별, 기준 ID·digest, 인계 source ID·digest와 지식저장소 보존 commit, 해당 코드·제품 digest, 이전에 발급한 작업 ID 범위다. 기존 원장과 충돌하면 이 경로로 덮어쓰지 않는다.

새 원장의 첫 항목은 제안하는 시스템 이벤트 `baseline.restored`로 둔다. `seq=1`, `prev_sha256=null`로 독립 체인을 시작하고, `ledgerId`·`projectId`·복구 시각·검증된 기준 참조와 digest를 연결한다. 기준 참조는 위 복구 메타데이터를 재사용한다. 이전 결정의 식별·해시나 보존 source 참조는 출처로만 연결하며 새 체인의 `prev_seq`·`prev_sha256`로 잇지 않는다. 같은 복구를 재시도하면 동일 기록을 재사용한다.

복구 이벤트는 Gate 승인 집계에서 제외하고 사용자 발언을 만들어 넣지 않는다. 현재 schema는 모든 이벤트에 사용자 발언 `quote`를 요구하므로 이 시스템 이벤트만 예외로 지원한다. 복구 경로에서는 원장 부재·빈 원장을 옛 `approval_audit`로 대체하는 기존 fallback을 사용하지 않는다. 과거 결정은 보존 source에서 대상·당시 계약 digest·선택 내용·출처를 조회하는 이력이지, 새 원장의 승인 이벤트나 새 작업의 실행 권한이 아니다. 현재 작업에 필요한 권한은 현재 요청과 기존 실행 계약 경로에서 얻는다.

따라서 모든 옛 문서나 원장 전체를 복원해야 다음 작업을 할 수 있는 구조를 피한다. 전체 과거 체인을 보존하지 않았다면 전체 체인 감사가 가능하다고 표시하지 않는다. 이 복구 이벤트·초기화 schema·validator·승인 판정 분리는 신규 구현 대상이며 현재 코드가 이미 허용하는 흐름이 아니다.

완료 이력을 축약해도 발급한 iteration/task ID의 범위는 보존한다. 폴더 삭제 후 번호가 초기화되어 이전 ID를 재사용하면 안 된다. 일반 이력 조회는 작은 완료 기록과 지식 참조를 사용하고 과거 작업 폴더를 재생성하지 않는다.

완료 기록에는 보관 위치가 로컬 산출물인지 인계된 근거인지 명시한다. 인계가 확인된 기록의 감사·이력 조회는 보존 source를 검증한다. 기존 기록은 기존 파일·해시 검증을 유지한다. 해시 검사 실패를 삭제 완료로 간주하거나 기존 승인 기록의 경로를 임의 치환하지 않는다.

관련 제안·리뷰·실패·복구 기록이 원본에 의존한다면 필요한 근거를 함께 인계하거나 해당 파일만 보존한다. 기존 `runs gc`와 성공 재시도 정리는 인계할 근거가 추출되기 전에 이를 없애지 않도록 연결한다. 문서 정리와 지식 보존 기능이 준비되기 전에는 현재 보관 동작을 확대하지 않는다.

## 7. 정리 동작

정리는 인계가 확인된 완료 작업에만 적용한다. 기본 구현은 다음 순서로 한다.

1. 정확한 작업 소유 경로, 현재 내용 해시, 공유·활성 참조를 읽어 정리 대상을 계산한다.
2. 보존 commit·본문 digest·필수 참조와 기준의 파싱·복구를 확인한다. 위키 채택이나 새 현재 기준으로 승격됐는지는 정리 조건으로 삼지 않는다.
3. 진행 중 작업과 충돌하지 않는 잠금 안에서 참조를 전환하고, 대상 파일의 변경 여부를 다시 확인한다.
4. 재생성할 수 없는 자료는 보존을 확인한 뒤 작업 공간에서 제거한다. 선택한 정책에 따라 짧은 복구 기간 동안 격리할 수 있으나, 영구 보관 폴더가 하나 더 생기는 구조는 피한다.
5. 결과에 정리한 경로·남겨둔 이유·복구 위치를 간단히 남긴다. 재실행은 이미 처리한 파일을 성공으로 취급하고 남은 대상만 확인한다.

나이·용량·파일명 패턴만으로 `.plan2agent` 전체를 삭제하지 않는다. symlink, 소유권 불명, 사용자 변경, 공유 참조가 있는 경로는 제외한다. 이미 파일이 없더라도 완료된 인계·전환 기록 없이 정리 성공으로 추정하지 않는다. 실제 사용자 폴더를 시험 삼아 제거하지 않는다.

매 인계의 검사는 보존 경로만 사용하는 직접 읽기와 작은 데이터 검증에 한정한다. 다음 iteration 생성·취소, 제품 테스트 전체 재실행, 위키 AI 재작성·승인은 정리 때마다 실행하지 않는다. 원본을 뺀 fixture에서 다음 개발과 다음 위키 갱신까지 검증하는 것은 구현·릴리스 호환성 테스트로 수행하고, 인계 형식·resolver·초기화 경로가 변경되면 다시 실행한다.

## 8. 구현 단위와 변경 위치

| 순서 | 결과 | 주요 변경 위치 | 완료 조건 |
| --- | --- | --- | --- |
| 1 | 진행 브리핑·방향 의견, 관련 기억 조회 | P2A 실행 skill/reference, 사람용 표현 가이드, `p2a_buildlore.mjs`, context routing, provider mirror 생성 | 의견으로 상태가 차단되지 않고, 실제 연결 조회와 fallback을 확인 |
| 2 | 위키 채택과 분리된 지식 인계·보존 source | BuildLore source manifest/management, 직접 조회, planned source resolver, activation, reconcile; P2A 인계 adapter | 위키 대기 상태도 원본 없이 근거·기준 조회. 별도 호환성 fixture에서 다음 위키 갱신·활성화 성공. 실제 원본은 아직 유지 |
| 3 | 코드에 맞는 완료 기준에서 새 개발·유지보수 시작 | `p2a_iteration_state.mjs`, `p2a_iteration.mjs`, `p2a_next_service.mjs`, tasks/execute/runs의 source 해석, 완료·인계·복구 schema와 validator | 직전 폴더 없이 next/open/abandon/maintenance·이력 조회·새 원장 초기화 가능. 지연 인계가 최신 기준을 되돌리지 않음 |
| 4 | 인계 후 문서 정리와 기존 프로젝트 전환 | 기존 run retention, artifact ownership/참조 해석, 정리 계획·복구, 패키지 문서 | 새 작업의 인계→정리→다음 개발을 실제 설치 형태에서 검증 |

첫 적용은 신규 완료 작업부터 한다. 과거 BuildLore 자료의 대량 이동·삭제는 이 기능의 자동 부작용으로 넣지 않는다. 기존 작업은 인계 및 참조 확인이 끝난 묶음부터 선택적으로 전환한다.

현재 2단계 구현은 명시적인 로컬 고정본, sanitizer를 통과한 불변 객체, 선택적 객체 단독 로컬 commit, 원본에 의존하지 않는 직접 조회까지다. 자동 완료 hook이나 기존 GC 연결은 아직 없으며 capture는 원본 정리 전에 실행해야 한다. 객체는 위키 대기 상태로만 저장하고 현재 개발 기준을 변경하지 않으므로 지연 인계도 기존 기준을 덮어쓰지 않는다. 원본 없는 위키 갱신·다음 작업 재개는 아직 검증 가능한 구현이 아니며 모든 보존 결과의 `cleanupEligible`은 `false`다.

지침 변경은 배포되는 `.agents` reference에 반영하고 `scripts/sync_cli_assets.mjs`로 mirror를 생성한다. `docs/`만 수정해서 설치된 agent 행동이 바뀌었다고 간주하지 않는다.

## 9. 수용 기준과 검증

### 개발비서 행동 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| 정상 구현이 진행됨 | 사용자 기능의 진전과 다음 행동을 설명. 단순 파일 수로 완료율을 추정하지 않음 |
| 현재 요청에 비해 구조가 커짐 | 관찰·영향·대안을 한 번 설명하고 요청된 개발 계속 |
| 사용자가 이전 권고와 다른 방향을 선택함 | 최신 선택 반영. 새 근거 없이 같은 의견이나 승인을 반복하지 않음 |
| 과거 Wiki와 현재 코드가 다름 | 기록 당시와 현재 사실을 구분. 확인하지 않은 사실은 불확실성으로 표시 |
| 첫 시도이며 관련 프로젝트 기억이 있음 | 제한된 읽기 조회를 활용. 미설정·실패·시간 초과도 정상 fallback |
| 테스트 코드만 있고 실행 결과가 없음 | 검증 완료라고 보고하지 않음 |

문구 snapshot 테스트는 출력 계약만 검사한다. 방향 의견의 적절성·반복 여부·사실과 추론의 구분은 위 시나리오의 agent 실행 대화로 평가한다. 실제 관찰 없이 사용자 개입 감소나 판단 품질 개선을 달성했다고 보고하지 않는다.

### 자료 수명 통합 시나리오

1. 반복 개발 완료 → 근거·기준 보존 → 위키 반영 대기 상태에서 참조 전환·작업 폴더 제거 → 보존 source 직접 조회 성공 → 새 작업 시작·취소·다시 시작 성공. 대기·기각된 진술을 승인된 사실로 표시하지 않음.
2. 위 상태에서 다음 source snapshot·위키 갱신·활성화와 채택된 generation의 memory·lookup 성공. 정리한 문서를 다시 요구하거나 기존 사실을 정리 때문에 stale 처리하지 않음.
3. 실패→해결 작업의 원인·수정·회귀 검증을 인계하고 원본 run 정리 후에도 근거 조회 가능.
4. maintenance 한 건을 정리해도 다른 대기·진행 중 작업, task 의존성, feature 기준 유지.
5. 보존·독립 조회·참조 전환 실패 또는 해당 대상을 바꾼 저장소 변경은 개발 완료를 바꾸지 않고 필요한 원본 보존. 같은 내용 재시도는 중복 없음. 위키 반영만 실패한 경우는 정리를 막지 않음.
6. 정리 중 중단·파일 수정·동시 새 작업 시작·symlink를 주입해 범위 밖 파일이 제거되지 않고 재개 가능함을 확인.
7. 사용자 문서, 코드, 제품 문서, 활성 실행, 공용 결정 원장이 보존됨을 확인.
8. 프로젝트가 다르거나 보존 digest가 변조된 인계는 사용하지 않음. 오래된 검증은 현재 코드 검증으로 승격하지 않음.
9. 새 checkout에서 코드와 지식저장소, 최소 설정만으로 적용 가능한 기준·이력 조회와 새 로컬 원장 초기화·다음 작업 시작 가능. 복구 이벤트·과거 승인·seq·이전 해시·옛 `approval_audit`를 새 승인으로 재생하지 않음. 복구 재시도는 중복 없고 기존 원장이 있으면 덮어쓰거나 체인을 자르지 않음.
10. 기존 로컬 보관 프로젝트의 next, resume, archive audit, 검증, close/open과 BuildLore 미사용 흐름이 유지됨.
11. 반복 개발 세 건과 유지보수 두 건을 연속 완료·인계·정리한 뒤, 과거 Gate·run·임시 설계·조사 문서가 작업 공간에 누적되지 않고 해당 지식을 조회할 수 있음. 현재 기준 캐시는 한 개이며 작업 ID는 재사용되지 않음.
12. A 인계 지연 → B 인계·기준 반영 → A 재시도에서 B의 현재 기준과 사실이 되돌아가지 않음. 중복·서로 다른 유지보수 범위·겹치는 변경도 각각 이력 보존 또는 검증된 통합으로 처리하며 개발은 차단하지 않음.
13. main R2 지식과 release R1 checkout, 분기된 코드 계보, 미커밋 변경, 검증 revision 미상, 작업 중 generation 변경에서 잘못된 기준을 현재 승인·검증으로 승격하지 않음. 활성 작업의 기준은 고정됨.
14. 정상 인계·정리 한 건은 직접 읽기·digest·참조·기준 복구 검사만 수행함. 다음 개발 생성·전체 제품 검사·위키 생성·승인 절차를 매번 호출하지 않음.

기존 P2A `current-development-first`, `next-decision`, `run-retention`, `buildlore-integration`, context/asset 및 npm package 테스트를 확장한다. BuildLore에서는 publication portability, source 관리, activation, reconcile, connected read 테스트를 확장한다. 실제 BuildLore CLI를 호출하는 cross-repository fixture로 명령 전달 stub 테스트의 공백을 보완한다.

## 10. 권장 결정

- 개발 중 의견과 진행 브리핑은 기본 행동으로 한다. 새 필수 reviewer, 승인 메뉴, 의견별 보고서를 추가하지 않는다.
- 지식저장소가 연결된 프로젝트는 관련 기억을 개발 첫 시도부터 제한적으로 참고한다.
- 개발 완료, 근거 보존, 위키 반영, 작업 문서 정리는 각각 결과를 표시한다. 보존·참조 전환 실패는 정리만 늦추며, 위키 승인 대기는 정리를 막지 않는다.
- 지식저장소에는 현재 유효한 내용과 필요한 근거를 남기고, P2A에는 현재 작업과 최소 실행 상태를 둔다.
- 다음 기준은 현재 코드에 맞춰 선택하고 작업 중에는 고정한다. 늦은 인계는 과거 이력으로 보존하며 최신 기준을 되돌리지 않는다. 새 환경은 검증된 기준에 연결된 새 원장으로 시작한다.
- 첫 배포의 자동 정리 기본값은 꺼짐으로 제안한다. 프로젝트에서 지식 인계·정리 정책을 선택하면 검증된 신규 완료 작업부터 자동 처리하고, 같은 범위의 작업마다 확인받지 않는다. 별도 격리 기간을 필수로 두지 않으며 보존 근거와 현재 기준은 지식저장소에서 복구한다. 폐기한 모든 중간 문서의 원상 복원을 보장하는 기능은 아니다.
- 첫 구현은 1번의 비서 행동·읽기 연결부터 시작한다. 삭제 기능은 2·3번의 독립 조회·갱신·다음 작업 검증이 통과한 후 연결한다.
