# 사람에게 보이는 표현 작성 가이드

## [한눈에]

사용자가 결정을 내리거나 진행 상태를 확인하는 화면은 전체 그림을 먼저 보여준다. 정확한 기계 계약은 그대로 유지하되, 사람이 읽는 문장에서는 무엇을 결정하고 결과가 어떻게 달라지는지 먼저 설명한다.

```text
전체 그림 → 사용자의 선택과 결과 → 실행 명령 → 세부 계약
```

## 1. 권위와 표현을 분리한다

- JSON, CLI 결과 코드, 해시와 검증 결과가 결정 권위다.
- Markdown과 터미널 출력은 JSON을 설명하는 표현층이다.
- 두 층이 다르면 JSON이 우선한다.
- 사람용 표현을 검증이나 실행 계약의 새로운 입력으로 사용하지 않는다.

## 2. 결정 화면은 세 층으로 쓴다

```text
[한눈에]
지금 결정하는 것: 사용자가 이해할 수 있는 결과
승인하면 → 다음에 일어나는 일
거부하면 → 돌아가서 고칠 부분

[실행 명령]
p2a ...

[세부 계약]
state, reason, 경로, 해시와 전문용어
```

`[한눈에]`에는 Gate 번호, constitution, spec, run, reasonCode, approval audit 같은 시스템 용어를 쓰지 않는다. 제품 자체의 도메인 용어는 정확한 이해에 필요할 때 사용할 수 있다. 비유를 강제하거나 유치한 말투를 사용하지 않는다.

## 3. 생성 Markdown은 전체 그림으로 시작한다

`intake.md`, `product-spec.md`, `implementation-plan.md`는 제목 바로 아래에 `## [한눈에]`를 둔다.

- 무엇을 만드는지 한두 문장으로 설명한다.
- 흐름이나 결과 관계가 있으면 작은 텍스트 도식을 먼저 보여준다.
- 필드명, 근거, 제약과 상세 구현 내용은 다음 섹션으로 내린다.
- 사람용 요약은 항상 같은 JSON에서 결정론적으로 생성한다.

## 4. task intent는 설명일 뿐이다

새 task는 정확한 계약을 모두 작성한 뒤 마지막에 `intent` 한 문장을 작성한다.

```text
이 task가 끝나면 누가 무엇을 새로 할 수 있게 되는가?
```

- 프로젝트 사용자가 주로 사용하는 언어로 작성한다.
- `intent`가 있으면 사람용 목록과 진행 출력에서 title보다 먼저 보여준다.
- 완료 판정은 항상 `acceptanceCriteria`와 실제 검증 증거를 사용한다.
- `intent` 변경은 task 실행 계약이나 기존 run 증거를 바꾸지 않는다.
- 구형 task graph에 `intent`가 없어도 title을 사람용 대체 문장으로 사용한다.

## 5. 변경 시 검증한다

- 사람용 렌더링은 exact-string 또는 결정론적 snapshot 테스트를 둔다.
- 사람용 렌더링 전후의 기계 JSON 직렬화 결과가 같아야 한다.
- `intent`가 없는 기존 task graph 검증을 유지한다.
- 평이한 표현을 위해 acceptance, validation, 증거 또는 fail-closed 조건을 약화하지 않는다.
